## 1. Existing Ygor assessment and reuse decisions

### 1.1 `fv_surface_mesh<T,I>` is not an intermediate topology representation

The public `fv_surface_mesh<T,I>` type is a mutable facet/vertex transport container. It does not encode strong identity domains, paired halfedges, retained-use lineage, occurrence partitions, transparent seams, contour roles, precision references, transactional ownership, or independent verification evidence.

Therefore:

- do not instantiate a temporary `fv_surface_mesh<T,I>` in Component 11;
- do not use public vertex indices as output-occurrence identity before Component 14;
- do not derive adjacency from `involved_faces`, face arrays, normals, colours, metadata, or coordinate equality;
- do not call public mesh cleanup, duplicate-vertex merging, remeshing, slicing, orientation, hole filling, or triangulation methods; and
- leave public-mesh index conversion and serialization to Component 14.

`vec2<T>` and `vec3<T>` may be used only as nominal payload types inside Component 03 bounded records or read-only projected audit values. Bare vector equality, ordering, length, distance, angle, dot, cross, or normalization must not determine topology.

### 1.2 `YgorMeshesHoles` is specifically unsuitable for production reuse

`FindBoundaryChains` and its helpers are not reusable for this component because they:

- build a representative map by epsilon-distance spatial search;
- intentionally weld nearby coordinates for adjacency;
- skip index-equal and representative-equal zero-length edges;
- operate on an already materialized public mesh rather than retained-incidence lineage;
- select an arbitrary remaining outgoing boundary candidate when a representative has more than one continuation; and
- expose only boundary chains, not reciprocal halfedges, occurrence fans, region membership, provenance, precision, resources, or transactional evidence.

`FillBoundaryChainsByZippering` is also prohibited here: it mutates a public mesh, drops short/duplicate-index edges, and triangulates, which belongs to later components.

`EnsureConsistentFaceOrientation` similarly builds tolerance-welded edge adjacency and mutates face winding. Component 11 already receives authoritative retained orientation and must fail on contradiction rather than reorienting output.

The files may remain as unrelated public utilities, but Component 11 must not call them. Their fixtures may be reused only as non-normative test input generators after converting expected topology into explicit Component 10 artifacts.

### 1.3 `YgorMeshesOrient` is not a valid fallback

`OrientFaces` uses epsilon-based duplicate handling, bounding-box seed heuristics, ray casting, and mutable face reversal. None of those operations is permitted in Component 11. Output orientation comes from Component 10 and source-facet semantics; a mismatch is a typed invariant failure.

### 1.4 `YgorMeshesVerification` is only a later smoke-check utility

`YgorMeshesVerification.h/.cc` validates public triangular meshes by public indices and edge counts. It does not reconstruct occurrence identity, one closed vertex link, transparent-seam consumption, contour topology, exact lineage, or paired-edge birth.

Do not use it as the producer or independent verifier for `polygonal_output_complex<T,I>`. Component 14 or 15 may call it as an additional public-mesh smoke test after triangulation and assembly, but its result cannot replace the Component 11 verifier.

### 1.5 Existing polygon routines belong to Component 12 and reject required Component 11 cases

`Monotone_Decomposition_2`, constrained Delaunay helpers, and related polygon code are not production providers for Component 11. In particular, the current monotone implementation normalizes away duplicate/collinear vertices, rejects repeated coordinates, zero-length edges, touching loops, and zero-area structures, and uses ordinary/`long double` area decisions rather than the Component 03 bounded result model.

Do not use these routines to classify Component 11 contours or to “clean” cycles. Component 12 may improve or wrap selected in-tree polygon algorithms under its own bounded contract. Component 11 may reuse only generic test fixtures and nominal visualization helpers.

### 1.6 Narrow reusable primitives

The following reuse is permitted only through the established bounded subsystem contracts:

- Component 01 strong IDs, owner tokens, checked integer arithmetic, resource reservations, cancellation, stage transactions, deterministic error arbitration, canonical codec primitives, SHA-256, diagnostics, and replay support;
- Component 03 canonical scalar-bit encoding, bounded point/reference validation, bounded projection, orientation, segment relation, containment, residual, parameter, interval, and area services;
- Component 17 deterministic execution services when available;
- standard-library contiguous storage, stable sorting, binary search, and iterative graph traversal.

The bare `orient_sign`, `point_on_*`, `segments_intersect_*`, and `point_in_polygon_*` APIs return insufficient evidence for topology-affecting uncertainty decisions. They may be implementation details beneath Component 03 only if Component 03 already wrapped and qualified them. Component 11 calls the structured Component 03 services, never the bare Boolean/sign APIs directly.

No existing Ygor graph utility satisfies the complete-key, strong-ID, deterministic canonicalization, resource, cancellation, replay, and independent-verification requirements. Implement the small graph/permutation machinery in `YgorMeshesBooleanBounded` using checked contiguous tables and CSR ranges.

## 6. Exact face-region formation and boundary extraction

### 6.1 Reciprocal continuation graph

Construct a graph whose vertices are retained surface uses and whose undirected edges are validated reciprocal transparent-continuation pairs. Build it from sorted complete continuation keys, not hashes or source array positions.

For every continuation pair require:

- exactly two directed records with opposite seam direction;
- exact matching seam lineage and endpoint occurrence requirements;
- compatible retained orientation, support semantic region, occurrence/multiplicity sheet, and owner lineage;
- both member incidences are audited `transparent-internal`;
- no selected carrier, topology-separation contact, incompatible coincidence boundary, or suppressed non-owner seam is crossed;
- reciprocal neighbour references and complete member equality.

Use checked CSR adjacency and iterative traversal. A union-find implementation may be used internally only if final classes are reconstructed and keyed by sorted complete member sets; union roots and union order must never escape.

### 6.2 Provisional continuation components

Each connected continuation component becomes a provisional region candidate. Validate all members share:

- one prescribed output orientation;
- one compatible source-facet semantic support class and frame lineage;
- one occurrence/multiplicity sheet;
- compatible precision/support contracts.

Assign provisional IDs only after sorting complete provisional keys.

### 6.3 Positive-area connectivity split

A transparent graph can contain zero-measure connectors that must not join two unrelated positive-area interiors. V1 therefore derives final regions from a second exact graph over positive-area retained uses:

- include a continuation edge only when Component 09/10 sector evidence states that the two retained positive-area interiors continue through that seam;
- exclude zero-measure-only support, contact-only bridges, and deferred delimiters from positive-area connectivity unless the predecessor explicitly certifies positive-area continuation;
- preserve excluded records in split evidence; do not convert them into geometric gaps or delete them.

Connected components of this positive-area graph are final positive-area region candidates. Zero-measure-only structures attach to the uniquely specified final region through predecessor lineage or become explicit zero-measure support records. If attachment is non-unique and topology-affecting, fail.

Final region IDs are assigned from sorted complete member sets and split evidence, never provisional ID or traversal order.

### 6.4 Oriented boundary-dart model

Represent each non-suppressed retained incidence as an oriented dart owned by one retained use. For every retained use, validate its cyclic incidence order and construct:

```text
face_next(dart) = next oriented incidence on the same retained use
face_prev(dart) = previous oriented incidence on the same retained use
seam_twin(dart) = reciprocal dart for transparent-internal incidences only
```

`face_next`/`face_prev` come from Component 09/10 authoritative oriented boundary order. They are not reconstructed from coordinates.

For every boundary dart `b`, define its final-region successor using the fixed V1 permutation:

```text
j = face_next(b)
while disposition(j) == transparent-internal:
    j = face_next(seam_twin(j))
return j
```

The walk must remain inside the same final region, occurrence/multiplicity sheet, and compatible support class. It may cross only validated transparent seams. It stops only on a realized boundary dart. The symmetric predecessor operation uses `face_prev` and the reciprocal seam.

Bound each walk by the exact number of darts in the region. Re-entering a state before finding a boundary, crossing a split boundary, reaching suppressed/consumed/unresolved disposition, or producing a non-boundary target is failure.

This permutation is the sole V1 boundary successor source. Do not use turning angle, projected polar order, nearest endpoint, source triangle order, or arbitrary choice among outgoing darts.

### 6.5 Exact boundary multiset and cancellation ledger

For each final region:

- collect all planned-edge/topology-separation/zero-measure boundary darts owned by member uses;
- consume both directions of every internal transparent seam through the dart permutation;
- record every seam crossing made while reducing atom boundaries to region boundaries;
- verify no transparent seam appears as a result edge;
- verify no planned boundary incidence is cancelled;
- preserve multiplicity-distinct or occurrence-distinct coincident incidences separately;
- compare the exact canonical boundary incidence multiset against Component 10 planned-edge directed members assigned to the region.

No projected overlap, coordinate equality, approximate collinearity, or opposite nominal segment test may cancel incidences.

## 7. Atomic paired-edge and halfedge materialization

### 7.1 Planned-edge validation

Sort Component 10 planned-edge occurrences by complete key. For each occurrence, validate before allocation:

- exactly two distinct directed retained-incidence members;
- opposite direction roles under the authoritative source-edge/carrier orientation;
- both audit rows require realized boundary uses;
- both map to final regions;
- start/end occurrence requirements map to exact reversed output occurrence endpoints;
- local endpoint ports belong to the mapped output occurrences and expected Component 10 fans;
- carrier/source interval, event endpoints, multiplicity, separation, ownership, and pair-feasibility evidence agree;
- the two uses are not both the same directed incidence or an unauthorized duplicate;
- a loop/zero-length topology case is explicitly tagged and contract-valid.

Cardinality, direction, endpoint, interval, owner, multiplicity, or fan mismatch is failure. Do not search for an alternative mate.

### 7.2 Pair-at-creation builder

Create a private `paired_edge_builder_record` containing both halfedges. Determine canonical halfedge slots from complete directed-halfedge keys. With checked arithmetic:

```text
edge_id       = dense edge index
halfedge_id_0 = 2 * dense edge index
halfedge_id_1 = 2 * dense edge index + 1
```

Populate both records together:

```text
h0.pair = h1.id
h1.pair = h0.id
h0.origin = h1.destination
h0.destination = h1.origin
h1.origin = h0.destination
h1.destination = h0.origin
```

Also populate incident final region, retained use/incidence, local endpoint ports/fan sectors, role/lineage, and direction. Validate the complete pair record, then append it to private stage storage in one operation. No artifact view exists until the stage commits, so a lone halfedge is never observable.

Successor, predecessor, and cycle fields remain explicitly unresolved builder fields until Section 8; unresolved fields cannot enter the immutable artifact.

### 7.3 Whole, split, carrier, coplanar, and degenerate roles

Materialize exactly the edge occurrence supplied by Component 10:

- one whole source edge when planned as one occurrence;
- one paired edge per selected source-edge interval;
- one paired edge per transverse carrier interval and multiplicity occurrence;
- one paired edge per coplanar overlap boundary occurrence;
- one paired edge for topology-separation contacts when planned;
- topology-distinct equal-parameter and equal-coordinate intervals as separate pairs.

Use Component 08 ordering and interval identities as authoritative. Component 11 may verify them but must not sort again from nominal coordinates or reconstruct a carrier from planes/lines.

### 7.4 Zero-nominal-length descriptor

For endpoints with equal bits or overlapping bounded envelopes, call the Component 03 bounded length service and publish:

- lower/upper length bounds;
- endpoint occurrence and coordinate-source identities;
- topological preservation reason;
- incident uses/regions/cycles when known;
- cleanup eligibility constraints from policy/predecessor evidence;
- Component 12 handling requirement.

Do not collapse, delete, merge, or silently downgrade the edge.

### 7.5 Carrier and source-edge balance

For every Component 08 source-edge sequence and carrier domain referenced by an output edge:

- consume the authoritative ordered interval/event member sequence;
- compare exact selected member identities and directions;
- verify starts/ends and open/closed chain obligations;
- preserve equal-parameter tie order by frozen lineage keys;
- verify every planned edge appears exactly once in one domain audit;
- verify closed loops balance and open carrier chains close through documented source-edge transitions;
- store canonical membership and balance evidence.

Counts are supplemental. Compare complete member sets and ordered keys. Missing start/end, duplicate member, definite order reversal, crossed planned topology, or undocumented gap fails.

## 8. Successor/predecessor relation and cycle extraction

### 8.1 Map boundary darts to halfedges

Create a bijection between every realized boundary audit row and one output halfedge. Transfer the final-region boundary-dart successor from Section 6 to the corresponding halfedge successor.

For each `h -> next(h)` require:

- `h.destination == next(h).origin` by output occurrence identity;
- both halfedges belong to the same final region;
- the destination/end port of `h` and origin/start port of `next(h)` are connected by the exact retained-sector/continuation walk;
- the transition remains inside one Component 10 occurrence fan and does not cross separation/multiplicity/owner boundaries.

Construct predecessors by inverse permutation and require exactly one predecessor per halfedge. Do not independently choose a predecessor.

### 8.2 Permutation validation

Before walking cycles, prove over the exact halfedge member set:

- successor is total and in range;
- predecessor is total and in range;
- `prev(next(h)) == h` and `next(prev(h)) == h`;
- successor/predecessor preserve region membership;
- every halfedge has indegree and outdegree exactly one;
- no suppressed/internal incidence maps to a halfedge;
- no boundary halfedge is omitted.

A failed permutation is `internal_invariant_error` unless it directly exposes a documented predecessor geometric ambiguity, in which case use the appropriate geometric failure.

### 8.3 Directed cycle extraction

Traverse successor cycles from the least unvisited complete halfedge key within each final region. For each walk:

- mark halfedges in a private visitation table;
- require closure at the starting halfedge and starting output occurrence;
- reject entry into any previously visited halfedge other than the start;
- reject reuse of a halfedge in the current walk;
- bound steps by the region boundary-halfedge count;
- collect ordered halfedges and ordered origin occurrence IDs;
- preserve the prescribed orientation.

After all walks, every output halfedge belongs to exactly one cycle.

### 8.4 Canonical cycle rotation and IDs

For each oriented cycle, compute the lexicographically least rotation of complete directed-halfedge keys using a deterministic linear-time minimal-rotation implementation or a checked `O(n log n)` reference for bounded small cycles. Rotation preserves direction. Never reverse the cycle.

Build the complete cycle key from the rotated sequence and region key. Sort all cycle keys globally before assigning IDs. Remap halfedge `cycle`, successor, and predecessor references after final cycle IDs are assigned.

Publish ordered halfedge/vertex references, source/carrier roles, support lineage, projected-area evidence reference, repeated-coordinate/degeneracy descriptors, and digest.

### 8.5 Repeated coordinates and short cycles

Cycle validity is topological. Do not reject a cycle merely because:

- two distinct vertex occurrences have equal nominal coordinates;
- the cycle visits the same nominal coordinate more than once through different occurrences;
- one boundary edge has zero nominal length;
- a deferred zero-measure cycle has fewer than three distinct nominal positions.

Tag these cases and route them to the contour/deferred-degeneracy contract. A positive-area cycle must still pass bounded noncrossing/orientation checks.

## 9. Contour roles, region finalization, and bounded admissibility

### 9.1 V1 contour representation

Freeze V1 face regions to:

- exactly one positive-area outer contour;
- zero or more direct positive-area hole contours;
- zero or more deferred zero-measure/occurrence-distinct contour records.

A positive-area island inside a hole is represented as a separate final face region with its own outer contour. Multiple unrelated positive-area outer contours force exact region splitting; V1 does not publish a multipolygon region.

### 9.2 Lineage-first role assignment

Determine contour role primarily from:

- final positive-area retained-use component membership;
- prescribed region orientation;
- source-facet semantic support and arrangement side lineage;
- oriented boundary incidence and local sector evidence;
- Component 10 separation/owner/multiplicity records.

Use bounded projected orientation/area as verification and only as a disambiguator when the predecessor contract explicitly leaves a geometrically decidable choice. Do not use nominal signed area alone.

For each cycle, request from Component 03 a structured projected signed-area result in the authoritative support frame. Record nominal value, enclosure, conditioning, symbolic exact-tie status, and provenance.

- A definite orientation matching the region's outer convention is an outer candidate.
- A definite opposite orientation is a hole candidate.
- A proven zero-measure cycle is deferred.
- An uncertain result that can change positive-area role requires aggregate lineage evidence or fails.

### 9.3 Single-outer enforcement and region-split validation

Section 6.3 is the only V1 phase allowed to split positive-area face regions. It completes before edge IDs, halfedge incident-region IDs, or cycle IDs are frozen. Contour analysis must validate that split; it must not perform a late topology rewrite.

For each final positive-area member component:

1. Classify all positive-area cycle candidates.
2. Require exactly one outer candidate after applying the exact Section 6 split evidence.
3. If several outer candidates correspond to different positive-area member components, report a producer region-split invariant failure because those components should already have separate final region IDs.
4. If several outer candidates remain in one exact positive-area component, V1 fails rather than publishing a multipolygon or guessing another split.
5. Attach each hole to the unique outer of its final region.
6. Require every positive-area island to already be represented by a separate final region and publish cross-region support-class nesting evidence where useful to Components 12 and 15.

No area-size threshold may drop or merge a contour.

### 9.4 Bounded containment verification

Prefer arrangement/member lineage to establish hole ownership. Independently verify containment using a deterministic bounded procedure:

- choose a least-key witness derived from an adjacent positive-area retained atom or a Component 09/10 certified interior sector, not a repeated boundary coordinate;
- project through the authoritative support frame using Component 03;
- compare against contour segment enclosures with a deterministic conservative sweep/ray direction derived from stable frame identity;
- return structured inside/outside/on-boundary/uncertain evidence;
- treat exact topology-distinct touches according to occurrence/separation lineage;
- fail if uncertainty could assign the hole to a different outer or change positive-area topology beyond tolerance.

Do not call the existing bare point-in-polygon helpers directly and do not choose a nominal epsilon offset.

### 9.5 Noncrossing and carrier-order admissibility

Build a deterministic per-support-region broad phase over conservative projected segment boxes. Use sorted endpoints/intervals or another in-tree contiguous sweep structure; do not use hash iteration order or an external spatial library.

For every candidate nonincident boundary-segment pair, call the Component 03 structured bounded segment-relation service. Classify:

- definite proper crossing not represented by an event -> failure;
- definite positive-length overlap without exact coincidence/owner lineage -> failure;
- exact endpoint/contact tie with documented topology separation -> valid and recorded;
- zero-measure overlap explicitly deferred -> valid only with a downstream obligation;
- uncertain relation capable of changing connectivity -> `geometric_condition_exceeds_tolerance`;
- definite disjoint -> valid.

Also verify:

- every endpoint is admissible for its source-edge/carrier interval;
- no authoritative event order admits a definite reversal;
- equal-parameter tie order matches frozen lineage keys;
- cycle orientation agrees with support orientation;
- no definitely self-crossing positive-area cycle is published;
- uncertainty accepted as deferred degeneracy is explicitly permitted by Component 12/13 policy.

Do not perform all-pairs checks in the scalable production path except below a frozen exhaustive threshold. The independent verifier may use all-pairs on bounded fixtures.

### 9.6 Deferred zero-measure topology

For every deferred cycle/edge/support publish:

- exact member halfedges and vertex occurrences;
- bounded area/length evidence;
- reason topology must remain;
- incident positive-area regions or explicit zero-measure-only ownership;
- permissible Component 12 representation and Component 13 cleanup constraints;
- lineage and replay witness.

Unexplained zero-measure structure is not accepted.

## 10. Vertex-link and complete topology verification

around_origin(h) = pair(prev(h))
